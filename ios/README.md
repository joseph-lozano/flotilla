# Flotilla for iPhone

The native iPhone app (Swift 6, SwiftUI, iOS 26+). It pairs with Flotilla servers and speaks the same WebSocket protocol as the Mac app and the CLI. Milestone 1 has the protocol client, pairing, and the Threads and Thread screens. Milestone 2 adds New thread, attachments, pairing by QR code, Settings, the PR bar's Fix / Resolve / Address review, opening a delegate's thread, and push notifications. The finish work after using it on a real iPhone adds naming the phone, long-press menus, Jump to latest, 120 Hz, haptics, the Dark and Tinted icons and the plum launch screen. Since then: Settings → Archiving, Undo for archives (yours and the server's), one prompt started on several models from New thread, search on Threads (titles as you type, then what was said in them; a hit opens its thread at that message), and one server per phone (pairing with another takes its place).

## Layout

- **`FlotillaKit/`**: the protocol client, a Swift package with no UI. It builds and tests on the Mac (`swift test`).
  - `JSON.swift`: a JSON value with serde_json's meaning of equality (`2` isn't `2.0`; objects are unordered), and its own parser. The replica applies deltas to views as these, exactly as Rust's does to `serde_json::Value`.
  - `Wire.swift`: the envelope (`Up`, `Down`), `ViewKey` (ordered as Rust orders it), requests and replies, notes (`pr_merged` with `archived`, `idle_archived`).
  - `Delta.swift` and `Replica.swift`: `flotilla_proto::delta::apply` and `flotilla_proto::Replica`, line for line. That covers revisions, the epoch, a resync on any doubt, and handing on only what changed.
  - `Session.swift`: `SessionCore`, `flotilla_client::session`'s, line for line: the session without the socket. Every frame from the server goes through it, the welcome and a refusal too. It decides what a hello holds, what to send again after a drop (by `welcome.seen`), what to fail when the server didn't keep the session, and which numbered messages (`n`) it already has.
  - `Client.swift`: `FlotillaClient`, an actor that keeps a connection up. It sends the token (`Authorization: Bearer`) and `flotilla-protocol: 1` on the upgrade, writes frames in order, pings every 20 s, and treats 45 s of silence as gone. It reconnects with jittered backoff from 250 ms to 10 s. `pause()` closes the socket when the app goes to the background, and `resume()` reconnects at once. A 401 is final.
  - `Transport.swift`: `URLSessionWebSocketTask`, behind a protocol so the tests can stand in a server.
  - `Pairing.swift`: `flotilla_proto::pair` (codes, `flotilla://pair?u=…#CODE` links, server addresses) and `POST /v1/pair`.
  - `QR.swift`: a pairing link from a picture of a QR code (Vision, else Core Image's detector, which is what the simulator uses), and drawing one for Add device.
  - `Requests.swift`: milestone 2's requests (`thread.new` with the client's UUID and, for one of several, its `branch_tag`; `thread.send` with files, `github.branches`, `pr.review_prompt`, `thread.on_branch`, `devices.pair`/`revoke`, `doctor.run`, `push.register`/`unregister`, `settings.set` for archiving) and the notes that answer in pieces (`branches`, `branch_checked`). `FanOut` is `new_thread.rs`'s rules for one prompt on several models: the requests, which carry a branch tag, and what refuses a start before anything is sent.
  - `History.swift`: long threads, as `flotilla_proto::history` pages them. `History` is a thread's older pages beside its view (which holds only its newest 100 to 149 messages, and every page's mark): what to fetch, what's still good by its mark, and what to show, line for line with Rust's. `Reading` fetches a page (`GET /v1/threads/:id/history?before=<seq>`) and a cut tool string whole (`GET /v1/threads/:id/full`), with the device's token.
  - `Search.swift`: `flotilla_proto::search`'s hits (`SearchHit`, its marks as UTF-8 byte ranges read leniently and as ranges of the snippet, and who Flotilla brought it from), `Request.search`, and `Search`: a query's words, whether a title has them all (any case or accent, each at the start of a word, as Rust's rules: `search.json`), and whether the server finds messages for it.
  - `Uploads.swift`: `PUT /v1/blobs` with the device's token, boat's limits on a prompt's files (12 files, 25 MB each, 64 MB in all, binary megabytes), and file kinds by name, as `flotilla_core::attach` has them.
  - `Limits.swift`: a thread's context and the agent accounts' usage limits (`flotilla_proto::limits`), with `flotilla_model::limits`'s rules: counts as T3 writes them, tones, a window whose reset has passed left out, the window that has used up a thread's account (one for another model alone doesn't count).
  - `AgentUsage.swift`: what the agents spent (`flotilla_proto::spend`, the `agent_usage` view: tokens by the hour and model, priced at list prices), and `Spend`, `flotilla_model::spend`'s rules: the last 30 days in the phone's own days, by model, cost by kind and speed, cache hits, T3's way of writing tokens and dollars, each provider's usage page.
  - `Services.swift`: Preview (`thread.preview`, answered with a URL) and a thread's services (`flotilla_proto::ThreadServices` in its view, and the `services` commands), with `thread_view.rs`'s rules: which services Preview's sheet shows (the VM it has now, while it's up), a service's state in words, which link Open opens, and the end of its output.
  - `PushRelay.swift`: the phone's side of the push relay (`relay/README.md`): `PushSeal` (CryptoKit's ChaChaPoly, the same bytes as `flotilla_core::push::seal`, checked against `relay/test/vectors.json`), `PushNote` (what the extension opens), `RelayClient` (register, refresh, unregister), and `RelayKeychain` (what the phone registered and the handles it left, in the Keychain group the app and its extension share).
  - `Models.swift`: the views the phone shows (sidebar, thread, catalog with effort and fast, settings with the server's checks and archiving, devices), read leniently. `Catalog.fit` and `Usage.startRoom` are Rust's, for several models. A field a newer server adds, or one it leaves out, is fine. Only a wrong shape makes a view unreadable, which is a doubt that triggers a resync.
- **`Flotilla/`**: the app. It is on the main actor by default (`SWIFT_DEFAULT_ACTOR_ISOLATION`), except the palette: SwiftUI resolves colours on its render thread too.
  - `Model/Phone.swift`: the phone's one paired server and the model of what it shows. Pairing (with the same server or another) and Forget make the model anew, so nothing one pairing showed, and no late answer to it, reaches the next.
  - `Model/AppModel.swift`: what the screens show, fed by its server's client in order (one server for the model's life), and what they can ask: starting threads (one per model chosen), uploads, the PR bar's prompts, Settings, the archive notice with Undo, and notifications (asking, registering the APNs token with the server, a tap opening its thread).
  - `Model/BranchChoice.swift`, `Model/Prompts.swift`: New thread's branch rows and search (`branch_picker.rs`), and the Fix and Resolve prompts word for word (`flotilla_core::fix`; Address review's comes from the server).
  - Search: Threads has a search field (`.searchable`; iOS 27 puts it at the bottom). Typing narrows the list to the threads whose titles have every word, with "In messages" from the server below once typing pauses (`search`). A hit opens its thread at the message: `AppModel` wants every page down to it (`History.reach`), fetching at most 4 at once and putting them in together, and the thread screen brings the row that shows it (`ThreadPlan.Plan.row(for:)`: its own, or the card a subagent's call or words are folded into, which opens) to the top, marked for a moment.
  - Long threads: `AppModel` keeps each open thread's `History` and fetches the pages it wants; the thread screen shows "Loading earlier messages…" above the oldest message shown and asks for the page above when it comes into sight; the first row on screen stays exactly where it is as the page goes in (`KeepPlace`). A tool output cut on the wire says so ("Cut to 32 KB of 328 KB"), with Show all (a sheet with the whole of it, in a text view that scrolls megabytes) and Copy all.
  - `Model/ThreadPlan.swift`: a thread's view as the rows its page shows, following the desktop's `thread_view.rs` and `subagents.rs`. That covers hand-off cards in place of the call that started them, "2 agents answered" lines, Claude Code `Agent` cards with their calls folded in, Codex spawns where they started, what this phone sent showing as sending, and streaming text while a turn runs.
  - `Model/Storage.swift`: the device token in the Keychain (this device only, after first unlock, keyed by the server's id), and the paired server in the defaults (no secrets). A phone that kept several servers (before one per phone) keeps the one it was using; the others' tokens are deleted, and each is asked to revoke the phone.
  - `Model/Relay.swift`: `RelayLink`, this phone's registration with the push relay for its server. Made only when the server's `push.register` answer says it sends through this phone's relay (`uses`), refreshed once a launch (a new token moves the handle; one the relay forgot is made again with a new key). Left on Forget, on pairing again, and when the server says it doesn't use the relay: at once, so the key is gone before Forget returns and no late answer brings it back (an epoch); the relay is then asked to forget the handle at later launches too, for up to a week. Each launch leaves a registration for a server the phone isn't paired with (`reconcile`). A Keychain that doesn't answer changes nothing.
  - `FlotillaApp.swift`: the app delegate for notifications (completion-handler forms: their `async` forms hand UIKit its answer off the main thread, which traps), the navigation path, and Appearance.
  - `Views/`: Threads, Thread (header, pinned subagents, rows, Jump to latest, the dock), a thread's commands (`ThreadMenu.swift`: a row's long-press and the thread's ⋯, as `thread_menu.rs`), the composer with its PR bar, Fix / Resolve / Address review and Hold to merge, New thread with its model and branch pickers, attachments, pairing with the camera's QR scanner, Settings with Add device, the usage sheet (`UsageSheet.swift`, from the counts' info button: boat's VMs, and an Agents tab, `AgentUsageView.swift`, with each account's weekly limits and the last 30 days' estimated cost, cache savings, cost by kind and speed, a trend by day and each model; subscribing to `agent_usage` while it's open checks the VMs, at most every five minutes), the context ring by Send and the agent limits beside the counts (`Limits.swift`: a tap on the ring gives its numbers, the account's logo and share opens the usage sheet on Agents), Preview (`PreviewSheet.swift`: the globe beside ⋯; a port field, or with services their sheet, each with Open, its links, Output and Restart / Stop / Start, and Another port…; what shows while the URL comes; the page in an in-app Safari view), markdown, the pixel sails and pips.
- **`FlotillaNotify/`**: the Notification Service Extension. A notification through the relay comes as "Flotilla: New activity" with the server's ciphertext (`e`); the extension opens it with the key from the shared Keychain group (`64D756D77S.com.useflotilla.flotilla.shared`) into the server's title, body, grouping and `flotilla` fields, so a tap opens the thread. One it can't open shows as it came.
- **`FlotillaTests/`**: the row planner, Hold to merge's timing, the time formats; the branch rows, the Fix and Resolve prompts against Rust's own text, the paired server and the move from several, a notification's server and thread (one from another server ignored), cards that open threads, and the archive notice's words.
- **`FlotillaUITests/`**: drives the app in the simulator against a real server and writes screenshots. This Mac has no simulator tap tool, so XCUITest does the tapping, typing and holding. `Support.swift` has what the suites share (`FlotillaUITestCase`: launching to Threads, pairing from a link, opening a thread, screenshots and notes) and the dev database's thread ids (`DevDB`). `MilestoneTwoUITests` covers milestone 2, the live run included, and pairing with a different server, Forget and a push from another server (a debug build launched with `-FlotillaKeychain` names the servers it has a token for, for the tests to check; `-FlotillaKeychainFails` is a launch whose Keychain doesn't answer); `PolishUITests` the finish work (naming the phone, the menus, Jump to latest, the home screen's icon styles); `ArchivingFanOutUITests` covers Archiving and several models. `ScheduleUITests` covers scheduled prompts: Scheduled from the clock on Threads, a thread's line over its composer and the prompt a schedule sent, and Send later from the composer and from New thread (pair with `test60Pair`, against a server whose database has schedules). `VideoUITests` plays the scenes of the 90-second video (`script/demo/flotilla-90s.sh phone`) while the host records the simulator. `SearchUITests` searches Threads (titles narrowed, messages from the server), opens the stress thread at turn 12 from a hit (page 3 of 62), checking it's on screen and stays, and checks a lone quote is no query and agents' answers say who they're from. `LimitsUITests` shoots the agent limits and the context ring on a database from a live run (`TEST_RUNNER_FLOTILLA_APPEARANCE` day or night). `AgentUsageUITests` shoots the usage sheet's Agents tab on `dev-db.py --usage --agent-usage`. `StartHereUITests` shoots the first screen on a server with no threads (New thread itself), on one whose setup fails (the checks, opened), a refused start coming back to it, and New thread opening the setup while threads can't run. `PagingUITests` opens `dev-db.py --stress`'s long thread (timing it), scrolls up until older messages load (pages slowed with `-FlotillaSlowHistory <ms>`, a debug-build launch argument, checking what's on screen stays put), and shows a cut tool output whole. `PreviewUITests` (pair with `test70Pair`, on `dev-db.py --project --services`) opens a thread's services sheet, a service's Output, Open in the in-app Safari view and Done back, Another port…, the port field with what shows while the URL comes (`-FlotillaSlowPreview <ms>`, a debug-build launch argument: an offline server refuses at once) and the refusal, a VM that wakes, and a services file with a problem (`TEST_RUNNER_FLOTILLA_APPEARANCE` day or night). `PublicLinksUITests` (pair with `test80Pair`, on `dev-db.py --project --services --public`) shoots public links: the header's open lock, a service public with time left and a port public until stopped (Copy link, Make private), Make public…'s four choices on a service and from the port field, and an offline server's refusals. `AppearanceUITests` (pair with `test1Pair`, on `dev-db.py`) opens Settings in Night, picks Day, Night and Phone in it and turns the phone dark and light under Phone, checking the open sheet's brightness each time.
- **`script/dev-db.py`**: a database for `flotilla serve --offline`, built from the real recordings in `/tmp`. `--project`, `--fix` and `--delegate` add a project, a pull request that needs fixing, and a delegate with its own thread; `--usage` and `--usage-tight` keep the account's usage (comfortable, or near its limits) for the usage sheet; `--agent-usage` 30 days of what the agents spent, their limits and the model prices for its Agents tab; `--stress [turns]` adds a long thread (about 3,100 messages, with huge tool outputs) for paging and capping; `--services` gives a thread services (ready with links, stopped, exited with its output), another a services file with a problem, and leaves one VM up without services and one stopped, for Preview (with `--public`, a service's link public for an hour and another port until stopped); `--empty` leaves no threads, as on a server just set up (a `blobs` folder beside its database that can't be written makes the database check fail).
- **`script/qr.swift`**: a pairing link as a QR code PNG, to add to the simulator's photos.
- **`script/icon-variants.swift`**: the icon's Dark and Tinted forms from `design/icons/AppIcon.png` (`swift ios/script/icon-variants.swift design/icons/AppIcon.png ios/Flotilla/Assets.xcassets/AppIcon.appiconset`).
- **`screenshots/`**: the milestone's proof, at half size; `archiving-*` and `fan-out-*` for Archiving and several models; `search-*` for search; `limits-*` for the context ring and agent limits; `agent-usage-*` for the usage sheet's Agents tab; `preview-*` for Preview, Day and Night.

`crates/flotilla-server/tests/conformance.rs` records the Rust side. It runs a real server (with a stand-in engine) and a raw WebSocket, and covers snapshots, deltas, a delta lost on the way, a drop that resumes and a restart. It writes `mobile/fixtures/conformance/session.json` (every frame each way, what Rust's replica made of each, and the final views) and `deltas.json` (170 `delta::diff` cases, including random reorders and page marks). `search.json` is search's rules: a query's words, whether it finds messages, and whether and where a text has them (the test fails if it's out of date). `history.json` is a long thread: its view's newest pages, older pages over HTTP as Rust's `History` wanted them, the view moving on, a message changing outside it, a lost delta, tool output cut (multibyte across the cut, a 2,000-line list, text that isn't JSON) and fetched whole. `FlotillaKit`'s `RustConformance` and `RustHistoryConformance` tests replay them and must end with identical views, wanting and showing exactly what Rust did.

## Decisions

- **XcodeGen.** `project.yml` is the project, and `Flotilla.xcodeproj` is generated (and ignored), so the project stays reviewable. Run `brew install xcodegen`, then `xcodegen` in `ios/`.
- **Bundle id `com.useflotilla.flotilla`**, team `64D756D77S`, automatic signing. A development build signs with the Apple Development identity and the team's wildcard profile. The app registers `flotilla://` and `flotilla-dev://`, the scheme a dev server's pairing links use.
- **iOS 26.0** at the least. It's tested on the iOS 27.0 simulator (iPhone 17).
- **Plain HTTP only to this network** (`NSAllowsLocalNetworking`): a server on this Mac or the LAN. A Tailscale server is `https://`.
- **Pairing takes a tap.** A `flotilla://pair` link fills in the form, but it never connects by itself.
- **No dependencies.** It uses Foundation's WebSocket, Security for the Keychain, SwiftUI, PhotosUI, AVFoundation for the camera, Vision and Core Image for QR codes, and UserNotifications.
- **One server.** Settings (the gear on Threads) names it, with Pair with a different server, which takes its place, and Forget, which goes back to pairing. Either way the old token leaves the Keychain at once, and the old server is asked to revoke this phone (so it stops sending it notifications) if it answers within four seconds. Threads doesn't name the server: the screen is for threads. A launch whose token is gone (a restore onto another phone: tokens stay on their phone) goes back to pairing; one whose Keychain doesn't answer keeps the pairing and says why, with Pair again.
- **No empty Threads.** With no thread (and none starting), Threads is New thread itself: Start sits in the bar beside the usage, the gear stays, and there's no search. A refused start comes back there with what was written and why. While a check threads can't run without fails (the boat key's or the database's, `stopsThreads`), it's the server's setup instead, opened, and New thread's sheet shows the setup too. Once there's a thread, archived or starting, it's the list.
- **New thread** opens the thread at once (its prompt marked as sending, then "Starting…") while its files go up and the server makes the VM. A refused start goes back to New thread with what was written. The model picker is a searchable sheet by agent (only the agents whose subagents Flotilla shows, as on the desktop); effort and fast are chips; the project and branch sit under the box, the branch picker fed by `github.branches` progress.
- **Photos go as JPEG**, at most 2048 pixels on a side (iPhone photos are HEIC, which not every model reads). Files from Files go as they are. boat's limits are checked as files are added and again before they go up.
- **Several models, one thread each.** The model sheet keeps a tap for one model (it picks and closes); **Select** at its top right turns the rows into checkmarks, in the order tapped, and **Done** takes them (it opens that way when several are chosen already). The chip names them all ("Opus 5.5 + GPT-6.1 Sol"). Effort and fast are the first model's; each other model gets the same level if it has it, else the nearest (`Catalog.fit`), and fast only if it has fast mode. Start sends one `thread.new` per model, each with its own UUID, the same prompt, project and branch choice, and the files uploaded once. In a project on a new branch each carries its model's name as `branch_tag`, so their branches differ. The first opens; the rest are listed under Working as starting until the server has them. Several models on an existing branch, or more than boat will start now (the least room left in the sidebar's usage), are refused in New thread before anything is sent. If some starts are refused, the rest stay and the alert names each model that didn't start; if none start, it's back to New thread as before.
- **Archive from a thread goes back to the list.** The thread menu's Archive archives it and pops to Threads, where the Undo is; Unarchive stays on the thread.
- **Undo for archives** is one quiet card above the New thread bar, for five seconds: "Archived 1 thread · Undo" for a swipe or the thread menu, and the same for what the server archives by itself: threads left idle ("Archived 2 threads") and a merged pull request's thread ("#12 merged · Archived"). Archives in those seconds join the card. While the app is open, the server's push about a merge the card told of doesn't show as well. A debug build's `FLOTILLA_TEST_NOTE` (UI tests only) feeds a note through the same handler, since an offline server never archives by itself.
- **Settings → Archiving**: a switch for archiving on merge, and a menu for idle days (Never, 3, 7, 14, 30). Each writes `settings.set` at once; a refusal puts the old value back and says why.
- **Pairing by QR code** fills in the form, as a link does; connecting still takes a tap. Where there's no camera (the simulator), "Use a photo of the code" reads one from Photos.
- **The phone's name.** iOS gives apps only "iPhone", so pairing asks for a name (filled in with the one this phone last went by, else "iPhone"), and Settings → Devices renames any device, this phone included (`devices.rename`, which any paired device or the server's own machine may send, as `devices.revoke`). The Mac and Linux app's Settings has the same Rename.
- **Long-press, where the Mac right-clicks.** A thread's row: Mark as read or unread, Archive or Unarchive, Rename…, Open the pull request, Delete… (it asks first: "Deletes its VM and its history"). A thread being deleted leaves the list at once and comes back if the delete fails; a new title shows at once. A prompt, steer or reply: Copy (a reply as its Markdown), and Select text, which opens it in a sheet to select part of it (SwiftUI's `Text` selects only the whole). A tool call: Copy command (or path: the whole of it, not its shortened line) and Copy output. A card: Open thread (a hand-off's) and Copy answer.
- **Jump to latest** shows once the page is more than 240 points above the newest: a round glass button at the bottom right, above the PR bar and composer (and the keyboard), where the right thumb is.
- **The dock is opaque**, as in the mockup: the page stops at it and never shows under or below the composer.
- **120 Hz** on a ProMotion iPhone (`CADisableMinimumFrameDurationOnPhone`). Nothing animates by a timer of its own: Hold to merge draws by `TimelineView(.animation)` (in whole 4 pt cells, by design), clocks tick once a second.
- **Haptics, only where they mean something:** Hold to merge reaching the end (a medium impact), a message or new thread that didn't go (an error), pairing that worked (a success). Reading a pairing code with the camera is a light tap.
- **The icon** has Dark (the sails on iOS's own dark ground) and Tinted (grey sails for iOS to tint) forms, made by `script/icon-variants.swift`. **The launch screen** is the app's ground: plum in Night, paper in Day. iOS draws it before the app runs, so it follows the phone's appearance, not the app's own Appearance setting.
- **Push.** The app asks once it's connected (Settings → Notifications shows what iOS allows: On; Off, with Open Settings for Flotilla's page in iOS's Settings; or Turn on, before it's asked; read again each time the app comes back), registers for remote notifications once they're allowed, and at every connection sends its server its APNs token (`push.register`: the token, `sandbox` for a debug build or `production`, its bundle id, and what it has with the push relay for that server, if anything). The server answers how it sends: through a relay (`{"push": {"relay": "<url>"}}`), or not (its own APNs key, or off; an older server's `done`). Only if it's this phone's relay does the phone register there (`RelayLink`) and send `push.register` again with the relay's URL, handle and secret and a key the phone made; otherwise it leaves the relay. A server with the app's APNs key sends to Apple directly; one through the relay seals each note with the phone's key and the time, and the extension opens it (a note sealed more than 25 hours ago shows as the neutral alert). A notification says which server and thread it's about (`{"flotilla": {"server", "kind", "thread"}}`): a tap opens the thread; one about the thread on screen doesn't show. One from another server (one the phone left, which couldn't be told) neither shows while the app is open nor opens anything. Both builds carry `aps-environment` and the Keychain groups (`Flotilla.entitlements`, `FlotillaNotify.entitlements`). The relay is Info.plist's `FlotillaPushRelay`, from the `FLOTILLA_PUSH_RELAY` build setting (`https://push.useflotilla.com`); a debug build launched with `-FlotillaPushRelay <url>` uses that one, and with `-FlotillaPushToken <hex>` uses that token if APNs gives the simulator none. `-FlotillaNotifications allowed|denied|notAsked` stands in for iOS's answer, for `NotificationsUITests` (pair with `test1Pair`) to shoot each state.

## Build, test, run

```sh
cd ios
(cd FlotillaKit && swift test)                       # the protocol client, with the Rust conformance fixtures
xcodegen
SIM=<an iPhone 17 simulator's UDID>
xcodebuild -scheme Flotilla -destination "platform=iOS Simulator,id=$SIM" -derivedDataPath build/dd test -only-testing:FlotillaTests
xcodebuild -scheme Flotilla -destination generic/platform=iOS -derivedDataPath build/dd-device build   # signed for a device
```

Against a local server:

```sh
cargo build -p flotilla-cli
python3 -I ios/script/dev-db.py /tmp/flotilla-ios/srv --pr --states
target/debug/flotilla serve --offline --data-dir /tmp/flotilla-ios/srv --port 7791 &
target/debug/flotilla pair --data-dir /tmp/flotilla-ios/srv      # a link
cd ios && TEST_RUNNER_FLOTILLA_LINK='<the link>' TEST_RUNNER_FLOTILLA_SHOTS=/tmp/shots \
  xcodebuild -scheme Flotilla -destination "platform=iOS Simulator,id=$SIM" -derivedDataPath build/dd test \
  -only-testing:FlotillaUITests/FlotillaUITests/test1Pairing     # then test2Threads … test5HoldToMerge
```

`xcrun simctl ui $SIM appearance dark` gives Night. `TEST_RUNNER_FLOTILLA_SHOT_PREFIX` names a second set of screenshots.

`test1Pair` registers with the relay (the offline server answers with the relay it's set up for) and gives the server what it got. The server's sender then seals a note about the thread and sends it to the relay (`relay_push_for_simctl`), and the relay asks the fake APNs for the neutral alert carrying it. `relay-push.sh` delivers that exact body through APNs' sandbox to the simulator's real token (`relayed_through_apns_sandbox`), as the deployed relay will. The simulator never runs a Notification Service Extension for `xcrun simctl push`, so without `APNS_KEY_FILE` the script falls back to it and only the neutral alert shows.
